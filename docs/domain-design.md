# Domain Design

## 개요

본 문서는 Dev Board 프로젝트에 현재 구현된 핵심 도메인의 관계와 비즈니스 규칙을 정의하고,
향후 추가할 수 있는 확장 도메인의 설계 방향을 기록하기 위한 문서이다.

---

## 설계 원칙

- 객체 중심으로 도메인을 모델링한다.
- 비즈니스 규칙은 가능한 한 도메인 중심으로 관리한다.
- 삭제 정책은 일관성을 위해 Soft Delete 전략을 우선 적용한다.
- 회원 역할(USER, ADMIN)에 따른 권한 정책을 명확히 분리한다.

---

## 공통 엔티티 정책

현재 구현된 주요 엔티티(Member, Board, Comment)는 생성일시와 수정일시를 관리한다.

- createdAt: 생성일시
- updatedAt: 수정일시

향후 확장 도메인을 엔티티로 구현할 때에는 각 도메인의 특성과 이력 관리 필요성을 고려하여 생성일시와 수정일시의 관리 여부를 결정한다.

---

## 도메인 관계 상세

### 현재 구현된 도메인 관계

#### 1. Member ↔ Board

- 하나의 Member는 여러 개의 Board를 작성할 수 있다.
- 하나의 Board는 반드시 하나의 Member에 의해서만 작성된다.

**Cardinality: One-to-Many(1:N)**

#### 2. Member ↔ Comment

- 하나의 Member는 여러 개의 Comment를 작성할 수 있다.
- 하나의 Comment는 반드시 하나의 Member에 의해서만 작성된다.

**Cardinality: One-to-Many(1:N)**

#### 3. Board ↔ Comment

- 하나의 Board는 여러 개의 Comment를 가질 수 있다.
- 하나의 Comment는 반드시 하나의 Board에만 속한다.

**Cardinality: One-to-Many(1:N)**

#### 4. Comment ↔ Comment

- `일반 댓글`과 `대댓글`은 동일한 Comment 도메인으로 관리한다.
  - `일반 댓글`은 부모 댓글을 가지지 않는 최상위 댓글을 의미한다.
  - `대댓글`은 하나의 부모 댓글을 가지는 댓글을 의미한다.
  - `부모 댓글`은 하나 이상의 대댓글을 가지는 일반 댓글을 의미한다.
- 하나의 일반 댓글은 여러 개의 대댓글을 가질 수 있다.
- 하나의 대댓글은 반드시 하나의 부모 댓글을 가진다.
- 대댓글은 다른 댓글의 부모 댓글이 될 수 없다.

**Cardinality: One-to-Many(1:N, Self Reference)**

### 향후 확장 도메인 관계

다음 관계는 아직 구현되지 않았으며, 관련 기능을 구현할 때 구체적인 구조와 정책을 확정한다.

#### 1. Board ↔ UploadFile

- 하나의 Board가 여러 개의 UploadFile을 가질 수 있는 구조를 고려한다.
- 하나의 UploadFile이 하나의 Board에 속하는 구조를 고려한다.

**예상 Cardinality: One-to-Many(1:N)**

#### 2. Member ↔ BoardLike

- 하나의 Member가 여러 개의 BoardLike를 가질 수 있는 구조를 고려한다.
- 하나의 BoardLike가 하나의 Member에 속하는 구조를 고려한다.
- 동일 회원과 동일 게시글 사이의 BoardLike가 중복되지 않도록 제한하는 방안을 고려한다.

**예상 Cardinality: One-to-Many(1:N)**

#### 3. Board ↔ BoardLike

- 하나의 Board가 여러 개의 BoardLike를 가질 수 있는 구조를 고려한다.
- 하나의 BoardLike가 하나의 Board를 대상으로 하는 구조를 고려한다.

**예상 Cardinality: One-to-Many(1:N)**

Member와 Board 사이에 발생하는 다대다 관계는 BoardLike를 중간 도메인으로 두어 해소하는 방안을 고려한다.

## 현재 구현된 핵심 도메인

### 1. Member

#### 역할

- `회원`을 나타내는 도메인

#### 주요 기능

- 회원가입
- 로그인 및 로그아웃
- 마이페이지 조회
- 회원정보 수정
- 회원탈퇴

#### 비즈니스 규칙

##### 회원가입

- 회원가입 시 이메일, 비밀번호, 닉네임, 성별을 입력받는다.
- 이메일을 로그인 ID로 사용한다.
- 이메일 형식 검증을 수행한다.
- 이메일은 중복될 수 없다.
- 닉네임은 중복될 수 없다.
- 탈퇴 회원의 이메일과 닉네임은 재사용될 수 없다.
- 비밀번호는 최소 8자 이상이어야 한다.
- 비밀번호는 BCrypt 해시 형태로 저장한다.
- 닉네임은 2글자 이상, 30자 이하로 제한한다.
- 성별은 `남성`, `여성`, `선택안함` 중 하나를 선택할 수 있다.
- 회원가입 시 일반 회원(`USER`) 역할을 부여한다.
- 회원가입을 통해 관리자(`ADMIN`) 역할을 부여할 수 없다.

##### 관리자 계정 생성

- 관리자 계정 생성 기능은 별도로 제공하지 않는다.
- 관리자 계정은 운영자가 데이터베이스에 별도로 등록한다.
- 관리자 계정의 비밀번호도 BCrypt로 해시하여 저장한다.

##### 로그인 및 로그아웃

- 로그인 시 이메일, 비밀번호를 입력받는다.
- 존재하지 않는 이메일과 비밀번호 불일치는 동일하게 처리한다.
- 탈퇴 회원은 로그인할 수 없다.
- 로그인 성공 시 세션을 생성한다.
- 로그아웃 시 로그인 상태를 해제한다.

##### 마이페이지

- 로그인 회원은 마이페이지에서 자신의 정보를 조회할 수 있다.
- 회원 상태, 역할, 이메일, 닉네임, 성별 정보를 확인할 수 있다.
- 비로그인 사용자는 마이페이지에 접근할 수 없다.
- 비로그인 사용자가 접근하는 경우, 로그인 페이지로 이동한다.
- 로그인 성공 시 원래 요청한 페이지로 복귀할 수 있다.
- 탈퇴 회원은 마이페이지에 접근할 수 없다.

##### 회원정보 수정

- 로그인 회원은 마이페이지에서 자신의 정보를 수정할 수 있다.
- 닉네임과 성별만 수정 가능하다.
  - 닉네임
    - 닉네임은 시스템 전체에서 유일해야 한다.
    - 다른 회원이 사용 중인 닉네임으로 변경할 수 없다.
    - 길이는 2자 이상, 30자 이하로 제한한다.
  - 성별
    - 성별은 자유롭게 변경할 수 있다.
- 이메일은 로그인 ID 역할을 하므로 수정할 수 없다.
- 역할은 수정할 수 없다.
- 상태는 수정할 수 없다.
- 탈퇴 회원은 회원정보를 수정할 수 없다.

##### 회원탈퇴

- 로그인 회원은 마이페이지에서 스스로 탈퇴할 수 있다.
- 탈퇴 회원의 복구 기능은 제공하지 않는다.
- 회원탈퇴 시 Soft Delete를 적용한다.
- 탈퇴 회원의 작성 게시글 및 댓글은 유지한다.
- 탈퇴 회원의 이메일과 닉네임은 재사용할 수 없다.

### 2. Board

#### 역할

- `게시글`을 나타내는 도메인

#### 주요 기능

- 게시글 작성
- 게시글 목록 및 상세 조회
- 게시글 목록 페이징
- 게시글 조회수 증가
- 게시글 수정
- 게시글 삭제

#### 비즈니스 규칙

##### 게시글 작성

- 로그인 회원만 게시글을 작성할 수 있다.
- 게시글 작성 시 제목, 내용, 카테고리를 입력받는다.
- 게시글은 반드시 하나의 카테고리를 선택해야 한다.
- 게시글 제목과 내용은 필수 입력값이다.
- 게시글 제목은 최대 100자까지 입력할 수 있다.
- 일반 회원은 공지사항 카테고리를 선택할 수 없다.
- 공지사항은 관리자만 작성할 수 있다.

##### 게시글 조회

- 로그인 여부와 관계없이, 누구나 게시글을 상세 조회할 수 있다.
- 삭제 게시글은 상세 조회할 수 없다.
- 게시글 상세 화면 조회 시 조회수를 증가시킨다.
- 로그인 여부, 작성자 여부 및 회원 역할과 관계없이 동일한 조회수 증가 정책을 적용한다.
- 쿠키를 이용하여 24시간 동안 동일 게시글의 조회수 중복 증가를 방지한다.
- 삭제 게시글의 조회수는 증가시키지 않는다.

##### 게시글 목록

- 로그인 여부와 관계없이, 누구나 게시글 목록을 조회할 수 있다.
- 게시글은 최신순으로 조회한다.
- 삭제 게시글도 목록에서 조회할 수 있다.
- 삭제 게시글은 `삭제된 게시글입니다.` 문구로 표시한다.
- 공지사항은 목록에서 `[공지]` 라벨과 강조 색상을 통해 시각적으로 구분한다.

##### 게시글 목록 페이징

- 게시글 목록은 페이지 단위로 조회한다.
- 한 페이지에 게시글을 15개씩 표시한다.
- 페이지 번호는 1부터 시작한다.
- 한 페이지 블록에 페이지 번호를 5개씩 표시한다.
- 이전/다음 페이지로 이동할 수 있다.
- 요청한 페이지 번호가 유효한 범위를 벗어나면 유효한 페이지로 보정한다.
- 페이지 번호를 눌러 특정 페이지로 이동할 수 있다.

##### 게시글 수정

- 로그인 회원만 게시글을 수정할 수 있다.
- 활성 게시글만 수정할 수 있다.
- 게시글 작성자만 수정할 수 있다.
- 관리자는 다른 회원의 게시글을 수정할 수 없다.
- 게시글 수정 시 제목, 내용, 카테고리를 수정할 수 있다.
- 게시글 수정 시 제목, 내용, 카테고리에도 게시글 작성과 동일한 입력 규칙을 적용한다.
- 공지사항 카테고리로의 변경은 관리자만 허용된다.

##### 게시글 삭제

- 로그인 회원만 게시글을 삭제할 수 있다.
- 삭제 게시글은 다시 삭제할 수 없다.
- 게시글 작성자 또는 관리자만 삭제할 수 있다.
- 게시글 삭제 시 Soft Delete를 적용한다.
- 게시글을 삭제해도 해당 게시글의 댓글은 함께 삭제하지 않는다.

##### 향후 확장 고려

- 운영 정책이 필요한 경우, 공지사항(NOTICE)과 고정(PINNED) 정책을 분리하는 방안을 고려한다.

### 3. Comment

#### 역할

- `댓글`을 나타내는 도메인

#### 용어 정의

- 별도의 구분이 필요한 경우를 제외하고, `댓글`은 `일반 댓글`과 `대댓글`을 모두 포함한다.
- `일반 댓글`은 부모 댓글을 가지지 않는 최상위 댓글을 의미한다.
- `대댓글`은 하나의 부모 댓글을 가지는 댓글을 의미한다.
- `부모 댓글`은 하나 이상의 대댓글을 가지는 일반 댓글을 의미한다.

#### 주요 기능

- 댓글 작성
- 댓글 조회
- 댓글 수정
- 댓글 삭제

#### 비즈니스 규칙

##### 댓글 작성

- 로그인 회원만 댓글을 작성할 수 있다.
- 활성 게시글에만 댓글을 작성할 수 있다.
- 댓글 내용은 필수 입력값이다. 공백으로만 이루어진 문자열은 허용하지 않는다.
- 댓글 내용은 최대 2,000자로 제한한다.
- 일반 댓글은 부모 댓글을 가지지 않는다.
- 대댓글은 반드시 하나의 부모 댓글을 가진다.
- 부모 댓글은 대댓글과 동일한 게시글에 속해야 한다.
- 대댓글 깊이는 1단계로 제한한다. 대댓글에는 다시 대댓글을 작성할 수 없다.
- 삭제된 일반 댓글에도 대댓글을 작성할 수 있다.

##### 댓글 조회

- 로그인 여부와 관계없이 누구나 댓글을 조회할 수 있다.
- 일반 댓글은 작성된 순서대로 표시한다.
- 대댓글은 부모 댓글 바로 아래에 작성된 순서대로 표시한다.
- 삭제 댓글은 `삭제된 댓글입니다.` 문구로 표시한다.
- 부모 댓글이 삭제되어도 해당 댓글의 대댓글은 조회할 수 있다.

##### 댓글 수정

- 로그인 회원만 댓글을 수정할 수 있다.
- 활성 댓글만 수정할 수 있다.
- 삭제 게시글의 댓글은 수정할 수 없다.
- 댓글 작성자만 수정할 수 있다.
- 관리자는 다른 회원의 댓글을 수정할 수 없다.
- 댓글 수정 시 댓글 작성과 동일한 입력 규칙을 적용한다.

##### 댓글 삭제

- 로그인 회원만 댓글을 삭제할 수 있다.
- 삭제 댓글은 다시 삭제할 수 없다.
- 삭제 게시글의 댓글은 삭제할 수 없다.
- 댓글 작성자 또는 관리자만 삭제할 수 있다.
- 댓글 삭제 시 Soft Delete를 적용한다.
- 부모 댓글이 삭제되어도 해당 댓글의 대댓글은 함께 삭제하지 않는다.

##### 향후 확장 고려

- 댓글 좋아요(CommentLike) 기능을 추가할 수 있다.

## 향후 확장 도메인

### 1. BoardLike

#### 역할

- `게시글 좋아요`를 나타내는 확장 도메인

#### 고려 중인 주요 기능

- 좋아요 등록
- 좋아요 취소

#### 설계 고려 사항

- 동일 회원이 동일 게시글에 중복으로 좋아요를 누를 수 없도록 제한하는 방안을 고려한다.
- 좋아요 취소 시 해당 BoardLike를 Hard Delete하는 방안을 고려한다.

---

### 2. UploadFile

#### 역할

- `첨부파일`을 나타내는 확장 도메인

#### 고려 중인 주요 기능

- 첨부파일 업로드
- 첨부파일 다운로드

#### 설계 고려 사항

- 하나의 게시글에 여러 개의 첨부파일을 등록할 수 있는 구조를 고려한다.
- 등록된 첨부파일을 다운로드할 수 있는 기능을 고려한다.
- 게시글이 Soft Delete된 경우 첨부파일 정보와 실제 파일을 어떻게 처리할지는 관련 기능을 구현할 때 결정한다.

## 권한 정책

### 공통 권한

- 로그인 회원은 게시글과 댓글을 작성할 수 있다.
- 작성자는 본인이 작성한 게시글과 댓글을 수정할 수 있다.
- 작성자는 본인이 작성한 게시글과 댓글을 삭제할 수 있다.

### USER

- 공지사항을 작성할 수 없다.

### ADMIN

- 공지사항을 작성할 수 있다.
- 다른 회원이 작성한 게시글과 댓글을 수정할 수 없다.
- 다른 회원이 작성한 게시글과 댓글을 삭제할 수 있다.

### 향후 확장 고려

- 관리자가 회원 상태(ACTIVE / DELETED)를 관리하는 기능을 고려한다.

## 삭제 정책

도메인 간 참조 무결성과 이력 보존을 위해 현재 구현된 Member, Board, Comment에는 Soft Delete를 적용한다.

| 삭제 정책       | DB 데이터 | 대상 도메인                       | 상태 변경            |
|-------------|--------|------------------------------|------------------|
| Soft Delete | 유지     | Member<br/>Board<br/>Comment | ACTIVE → DELETED |

### 향후 확장 도메인 고려 사항

- BoardLike는 좋아요 취소 시 Hard Delete를 적용하는 방안을 고려한다.
- UploadFile은 게시글이 Soft Delete된 경우, 첨부파일 정보와 실제 파일을 어떻게 처리할지 관련 기능을 구현할 때 결정한다.

## 인증 및 인가 정책

### 인증

- 이메일과 비밀번호를 이용하여 로그인한다.
- 비밀번호는 BCrypt 해시하여 저장하며, 평문 비밀번호는 저장하지 않는다.
- 세션 기반 인증 방식을 사용한다.
- 로그인 성공 시 세션을 생성하고, 세션에는 로그인 회원의 ID만 저장한다.
- 로그아웃 시 세션을 무효화한다.
- 회원탈퇴 시 세션을 무효화한다.
- 탈퇴 회원은 로그인할 수 없다.

### 로그인 확인 및 사용자 식별

- 로그인 필수 요청의 로그인 여부는 `LoginCheckInterceptor`에서 확인한다.
- `LoginCheckInterceptor`는 세션에 로그인 회원 ID가 존재하는지만 확인한다.
- 로그인 필수 요청에서 세션에 로그인 회원 ID가 없으면 미인증 상태로 판단한다.
  - 처음부터 로그인하지 않은 경우
  - 로그인 후 세션이 만료된 경우
- 실행 대상 Handler의 `@RestController`와 `@ResponseBody` 적용 여부를 기준으로
  SSR 요청과 API 요청을 구분한다.
  - SSR 요청
    - 로그인 페이지로 redirect한다.
    - 로그인 성공 후 원래 요청 경로로 복귀할 수 있도록 서버에서 복귀 URL을 구성한다.
  - API 요청
    - `LOGIN_REQUIRED` 코드와 메시지를 포함한 JSON을 `401 Unauthorized` 상태로 반환한다.
    - 로그인 성공 후 브라우저의 현재 화면으로 복귀할 수 있도록
      클라이언트에서 복귀 URL을 구성한다.
- 로그인 회원 ID는 `LoginMemberIdArgumentResolver`를 통해 Controller에 전달한다.
- `LoginCheckInterceptor`와 `LoginMemberIdArgumentResolver`는
  회원의 존재 여부나 `ACTIVE` 상태를 검증하지 않는다.
- 회원의 존재 여부와 `ACTIVE` 상태는 실제 유스케이스를 수행하는 Service에서 최종 검증한다.
- 로그인 확인, 로그인 회원 식별 및 회원 상태 검증의 책임을 분리한다.

### 인가

- 로그인 여부, 회원 역할 및 작성자 여부를 기준으로 요청 수행 권한을 확인한다.
- 공개 조회가 허용된 경로를 제외한 게시글 및 댓글 기능은 로그인 회원만 이용할 수 있다.
  - 게시글 목록, 게시글 상세, 댓글 목록은 로그인 여부와 관계없이 조회할 수 있다.
- 구체적인 역할별·작성자별 권한은 `권한 정책`을 따른다.
