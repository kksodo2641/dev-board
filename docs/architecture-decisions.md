# 1. 핵심 설계 원칙

## AD-001. DTO 기반 계층 분리

### 배경

초기 CRUD 프로젝트는 Entity를 Controller와 View까지 직접 전달하는 경우가 많다.

하지만, 화면 요구사항과 도메인 모델은 서로 다른 변경 주기를 가지며, Entity를 외부에 직접 노출할 경우 계층 간 결합도가 증가한다.

### 결정

Controller와 Service는 DTO를 통해 데이터를 주고 받는다.

Entity는 Service 내부에서만 사용하며, View 계층에 직접 노출하지 않는다.

```text
Controller
    ↓
   DTO
    ↓
 Service   
    ↓
  Entity
    ↓
Repository
```

### 결과

- 계층 간 결합도 감소
- 화면 요구사항과 도메인 모델 분리
- View 변경이 Entity 변경으로 전파되지 않음
- 응답 데이터 구조를 독립적으로 설계 가능

## AD-002. Service 중심 비즈니스 로직 관리

### 배경

Controller에 비즈니스 로직이 위치하면, 요청 처리와 도메인 규칙이 혼재된다.

또한, 동일 규칙이 여러 Controller에 중복될 가능성이 높다.

### 결정

비즈니스 규칙은 Service 계층에서 처리한다.

Controller는 다음 역할만 수행한다.

- 요청 수신
- Service 호출
- Model 구성
- View 반환

### 결과

- 비즈니스 규칙 집중
- Controller 단순화
- 테스트 용이성 향상
- 정책 변경 시 영향 범위 감소

# 2. 인증 및 사용자 식별

## AD-003. ACTIVE 회원 검증 책임을 Service 계층으로 집중

### 배경

초기 구현에서는 다음 계층들 모두 ACTIVE 회원 검증을 수행했다.

```text
LoginCheckInterceptor
LoginMemberIdArgumentResolver
Controller
Service
```

즉, 동일한 검증 로직이 여러 계층에 중복되어 존재했다.

### 문제

- 검증 로직 중복
- 책임 경계 불명확
- 정책 변경 시 수정 범위 증가

### 판단

ACTIVE 회원 여부는 인증 정책이 아니라, 비즈니스 정책에 가깝다.

### 결정

ACTIVE 회원 검증 책임을 Service 계층으로 집중시켰다.

각 계층의 역할을 다음처럼 분리했다. 

- Interceptor
  - 로그인 여부 확인

- ArgumentResolver
  - 사용자 식별

- Service
  - ACTIVE 회원 검증
  - 비즈니스 규칙 처리

### 결과

- 인증 / 비즈니스 규칙 분리
- 검증 로직 중복 제거
- 책임 경계 명확화
- 정책 변경 시, 수정 범위 최소화

## AD-005. LoginMemberId ArgumentResolver 도입

### 배경

Controller에서 HttpSession을 직접 사용하면, 인증 정보 접근 코드가 반복된다.

### 결정

Controller에서 세션을 직접 다루지 않는다.

로그인 사용자 식별은 ArgumentResolver를 통해 수행한다.

예시

```java
public String writeForm(@LoginMemberId Long memberId) {
}
```

### 추가 결정

로그인 검증을 통과한 요청에서 사용자 ID를 찾을 수 없는 경우는, 정상 흐름에서 발생할 수 없는 상황으로 판단했다.

따라서, 해당 경우는 IllegalStateException을 발생시켜 시스템 오류로 간주한다.

즉, 이는 시스템 불변식(Invariant) 위반으로 간주한다.

### 결과

- Controller의 세션 의존성 제거
- Controller의 인증 관련 코드 제거
- 인증 정보 접근 방식 통일
- 시스템 불변식(Invariant) 보호

## AD-006. 로그인 후 원래 요청 페이지 복귀

### 배경

비로그인 사용자가 인증이 필요한 페이지를 접근하려 하면, 로그인 화면으로 이동한다.

로그인 성공 후 원했던 페이지로 다시 이동하지 못하면 사용자 경험이 저하된다.

### 결정

로그인 페이지 이동 시, 원래 요청 URL을 포함시켜 전달한다.

로그인 성공 후 요청 URL로 복귀시킨다.

Query String을 포함하며, URL Encoding을 적용한다.

### 결과

- 사용자 경험 향상
- 인증 흐름 자연화

# 4. 데이터 관리 정책

## AD-008. Soft Delete 정책 채택

### 배경

데이터 물리 삭제 시, 추적이 어려워지고 연관 데이터 처리 문제가 발생한다.

특히 게시글, 댓글, 좋아요 등의 기능은 삭제 이후에도 관계를 유지할 필요가 있다.

### 고려한 대안

#### Hard Delete

실제 데이터를 DB에서 물리 삭제한다.

#### Soft Delete

상태값(status)만 변경한다.

### 결정

Soft Delete 정책을 채택했다.

적용 대상

- Member
- Board

### 결과

- 데이터 보존
- 데이터 감사(Audit) 가능
- 향후, 댓글 및 좋아요 기능 확장에 유리

---

## AD-009. 탈퇴 회원 이메일 및 닉네임 재사용 금지

### 배경

Soft Delete 적용 시, 기존 회원 정보의 재사용 여부를 결정해야 했다.

### 결정

탈퇴 회원의 이메일과 닉네임의 재사용을 허용하지 않는다.

### 이유

- 사용자 식별 일관성 유지
- 데이터 추적 가능성 확보
- 운영 정책 단순화

### 결과

- 회원 이력 보존
- 동일 식별자 재사용 방지

---

## AD-010. Entity 캡슐화 정책

### 배경

Setter 기반 설계는 Entity 상태를 외부에서 자유롭게 변경할 수 있게 만든다.

이로 인해, 데이터 변경 지점의 추적이 어려워지는 문제가 발생한다.

### 결정

Setter를 사용하지 않는다.

상태 변경은 의미 있는 메서드를 통해서만 수행한다.

예시

```text
member.withdraw();
member.changeNickname();
board.delete();
```

### 결과

- 무분별한 상태 변경 방지
- 도메인 규칙 보호
- 상태 전이 규칙 보호
- 객체지향적 모델링 강화

# 5. 게시판 설계

## AD-011. 게시판 페이징 직접 구현

### 배경

Spring Data JPA는 페이징을 편리하게 처리할 수 있는 Page와 Pageable을 제공한다.

하지만, 내부 동작 원리를 이해하지 못한 상태에서 사용하는 것은 학습 효과가 낮다고 판단했다.

### 결정

게시판 페이징을 직접 구현했다.

직접 구현 요소

- 전체 게시글 수(totalCount) 조회
- 전체 페이지 수(totalPages) 계산
- 페이지 블록 계산
- 페이지 블록의 시작/종료 페이지 계산
- 이전/다음 페이지 이동
- 페이지 보정(clamp)

### 결과

- 페이징 동작 원리 학습
- Spring Data JPA의 Page/Pageable 이해 기반 확보

## AD-013. Clamp 기반 페이지 보정 정책

### 배경

사용자가 비정상적인 페이지 번호를 요청할 수 있다.

예시
```text
?page=-10
?page=99999
```

### 고려한 대안

#### 예외 발생

잘못된 페이지 번호 요청 시, 오류를 발생시킨다.

#### Clamp

잘못된 페이지 번호 요청 시, 유효 범위 내로 자동 보정시킨다.

### 결정

Clamp 정책을 채택했다.

예시
- page < 1 → 첫 번째 페이지로 보정
- page > totalPages → 마지막 페이지로 보정

### 이유

실제 게시판 서비스의 사용자 경험과 더 유사하다고 판단했다.

### 결과

- 사용자 경험 향상
- 예외 상황 감소

## AD-014. 이전/다음 페이지 이동 방식 채택

### 고려한 대안

#### 블록 이동 방식

- `이전` 버튼을 클릭하면, 이전 블록으로 이동한다.
- `다음` 버튼을 클릭하면, 다음 블록으로 이동한다.

#### 페이지 이동 방식

- `이전` 버튼을 클릭하면, 이전 페이지로 이동한다.
- `다음` 버튼을 클릭하면, 다음 페이지로 이동한다.

### 결정

페이지 이동 방식을 채택했다.

### 이유

- 대부분의 서비스는 페이지 이동 방식을 사용
- 사용자는 페이지 블록 개념을 인식하지 않음
- 직관적인 사용자 경험 제공

### 결과

- UI 단순화
- 사용성 향상

## AD-018. 게시글 수정 권한 정책

### 배경

게시글 수정 권한을 누구에게 부여할 것인지 결정해야 했다.

특히, 관리자에게도 다른 사용자가 작성한 게시글의 수정 권한을 부여할지 여부를 검토했다.

### 고려한 대안

#### 작성자만 수정 가능

게시글 작성자만 자신의 게시글을 수정할 수 있도록 한다.

#### 작성자 및 관리자 수정 가능

관리자에게도 다른 사용자가 작성한 게시글의 수정 권한을 부여한다.

### 결정

게시글은 작성자만 수정할 수 있도록 결정했다.

### 이유

게시글 수정은 작성자가 작성한 내용과 의도를 변경하는 행위이다.

관리자 권한으로 다른 사용자의 게시글을 수정하는 것은 작성자의 의도를 변경할 수 있다고 판단했다.

또한, 대부분의 게시판 서비스는 게시글이 수정되면 수정 사실이 사용자에게 표시된다.

관리자가 작성자의 게시글을 수정할 경우, 작성자는 자신이 수정하지 않았음에도 게시글이 수정된 것으로 표시되어 혼란을 겪을 수 있다.

관리자의 역할은 서비스 운영에 있으며, 콘텐츠를 대신 수정하는 역할과는 구분되어야 한다고 판단했다. 

### 결과

- 게시글 작성자의 의도 보존
- 운영 권한과 콘텐츠 소유권 분리
- 관리자와 작성자 역할 명확화

## AD-019. 게시글 삭제 권한 정책

### 배경

게시글 삭제 권한을 누구에게 부여할 것인지 결정해야 했다.

특히, 관리자에게도 다른 사용자가 작성한 게시글의 삭제 권한을 부여할지 여부를 검토했다.

### 고려한 대안

#### 작성자만 삭제 가능

게시글 작성자만 자신의 게시글을 삭제할 수 있도록 한다.

#### 작성자 및 관리자 삭제 가능

관리자에게도 다른 사용자가 작성한 게시글의 삭제 권한을 부여한다.

### 결정

게시글은 작성자와 관리자 모두 삭제할 수 있도록 결정했다.

### 이유

게시글 삭제는 작성자의 의도를 변경하는 수정과 달리, 서비스 운영 및 관리 영역에 해당한다고 판단했다.

관리자는 커뮤니티 운영의 책임자로서, 운영 정책에 위반되는 게시글이나 부적절한 게시글을 신속하게 조치할 수 있어야 한다.

따라서, 관리자는 게시글 내용을 직접 수정하는 대신, 서비스 운영을 위해 필요한 경우 게시글을 삭제할 수 있도록 결정했다.

### 결과

- 서비스 운영 정책 적용 가능
- 운영자 권한과 콘텐츠 소유권의 역할 분리
- 부적절한 게시글에 대한 신속한 대응 가능

## AD-020. 권한 기반 UI 표시 정책

### 배경

게시글 상세 화면에서 수정 및 삭제 버튼의 노출 여부를 결정해야 했다.

수정과 삭제는 서로 다른 권한 정책을 가지므로, 단순히 작성자 여부만으로는 버튼 노출을 결정할 수 없었다.

### 고려한 대안

#### Controller에서 권한 계산

Controller에서 `canEdit`, `canDelete` 값을 계산하여 View에 전달한다.

#### Service에서 권한 계산

BoardService에서 `canEdit()`, `canDelete()` 메서드를 제공하여 권한 여부를 반환한다.

#### Permission DTO 도입

수정, 삭제 등 화면에서 필요한 권한 정보를 하나의 DTO로 구성하여 View에 전달한다.

### 결정

현재 프로젝트에서는 Controller에서 `canEdit`와 `canDelete`를 계산하여 View에 전달하도록 결정했다.

### 이유

현재 권한 정보는 게시글 상세 화면에서만 사용되며, 필요한 정보도 `canEdit`, `canDelete` 두 가지로 단순하다.

이러한 상황에서 UI 표시만을 위한 별도의 Service 메서드나, Permission DTO를 도입하는 것은 현재 프로젝트 규모에 비해, 과도한 설계라고 판단했다.

또한, 현재 구조에서 별도의 Service 메서드를 사용할 경우, 이미 조회한 게시글 정보를 활용하지 못하고 동일 게시글에 대한 재조회가 발생할 수 있다고 판단했다.

특히, 수정 및 삭제 권한에 대한 실제 검증은 `BoardService`에서 수행하므로, Controller에서는 화면 표시를 위한 권한 정보만 계산하도록 역할을 분리했다.

### 결과

- View는 전달받은 권한 정보만 이용하여 버튼 노출 여부 결정
- UI 표시와 실제 권한 검증의 책임 분리
- 현재 프로젝트 규모에 적합한 단순한 구조 유지
- 권한 정책이 복잡해질 경우, Permission DTO 또는 별도 권한 객체 도입 가능

## AD-021. 권한 검증 로직의 도메인 캡슐화

### 배경

초기 구현에서는 게시글 작성자 여부를 확인하기 위해, `BoardService`에서 게시글 작성자 ID와 회원 ID를 직접 비교했다.

### 결정

작성자 여부를 판단하는 책임을 `Board` 엔티티의 `isWriter()` 메서드로 이동시켰다.

### 이유

게시글 작성자 여부는 게시글이 스스로 알고 있어야 하는 '도메인 규칙'이라고 판단했다.

Service에서 작성자 ID를 직접 비교하기보다, `Board`가 자신의 작성자인지를 판단하도록 하여, 도메인 객체가 자신의 규칙을 직접 표현하도록 했다.

이를 통해, Service는 권한을 판단하는 대신, 권한 검증을 수행하는 역할에 집중하도록 했다.

### 결과

- 도메인 규칙의 캡슐화 강화
- Service의 책임 감소
- 도메인 객체의 의도 표현 향상
- 권한 검증 코드의 가독성 향상

# 7. 학습 목적 설계 결정

## AD-017. Spring Data JPA Page/Pageable 미사용

### 배경

Spring Data JPA는 강력한 페이징 기능을 제공한다.

그러나, 내부 동작 원리를 이해하지 못한 상태에서 사용하는 것은 학습 효과가 낮다고 판단했다.

특히, 기능 구현 자체보다 동작 원리를 이해하는 과정을 중요하게 생각했다.

### 결정

초기 구현에서는 Spring Data JPA의 페이징 기능을 사용하지 않고, 직접 구현했다.

### 이유

페이징 동작 원리를 먼저 이해하기 위함이다.

### 결과

- 페이징 동작 원리 학습
- Page/Pageable 추상화 이해 기반 확보
- 직접 구현 방식과 프레임워크 기능 비교 경험 확보

### 향후 계획

직접 구현한 방식과 Spring Data JPA의 Page/Pageable을 비교 분석한 뒤 리팩토링을 진행할 예정이다.
