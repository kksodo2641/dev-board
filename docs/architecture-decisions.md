단순히 현재 구조를 설명하는 것이 아니라, 다음 내용을 함께 기록하는 것을 목표로 한다.

# 1. 핵심 설계 원칙

## AD-001. DTO 기반 계층 분리

### 배경

초기 CRUD 프로젝트는 Entity를 Controller와 View까지 직접 전달하는 경우가 많다.  
하지만 화면 요구사항과 도메인 모델은 서로 다른 변경 주기를 가지며, Entity를 외부에 직접 노출할 경우 계층 간 결합도가 증가한다.

### 결정

Controller와 Service는 DTO를 통해 데이터를 주고 받는다.  
Entity는 Service 내부에서만 사용하며, View 계층에 직접 노출하지 않는다.

```text
Controller
    ↓
   DTO
    ↓
 Service
    ↓
  Entity
    ↓
Repository
```

### 결과

- 계층 간 결합도 감소
- 화면 요구사항과 도메인 모델 분리
- View 변경이 Entity 변경으로 전파되지 않음
- 응답 데이터 구조를 독립적으로 설계 가능

## AD-002. Service 중심 비즈니스 로직 관리

### 배경

Controller에 비즈니스 로직이 위치하면, 요청 처리와 도메인 규칙이 혼재된다.  
또한, 동일 규칙이 여러 Controller에 중복될 가능성이 높다.

### 결정

비즈니스 규칙은 Service 계층에서 처리한다.

Controller는 다음 역할만 수행한다.

- 요청 수신
- Service 호출
- Model 구성
- View 반환

### 결과

- 비즈니스 규칙 집중
- Controller 단순화
- 테스트 용이성 향상
- 정책 변경 시 영향 범위 감소

## AD-034. Service 계층과 Entity의 책임 분리

### 배경

Dev Board는 Member, Board, Comment 등 여러 도메인을 다루며,  
하나의 유스케이스 안에서 여러 도메인 객체와 Repository를 함께 사용할 수 있다.

기능이 늘어날수록 다음 기준을 명확히 할 필요가 있었다.

- 사용자 요청 검증은 어디에서 수행할 것인가?
- 존재 여부와 권한 검증은 어디에서 수행할 것인가?
- Entity는 어디까지 책임질 것인가?
- Service와 Entity가 같은 정책을 중복으로 검증하는 것은 어떤 의미를 가지는가?

### 고려한 대안

#### Service에 모든 로직 집중

Service가 요청 검증, 권한 검증, 상태 변경, 도메인 규칙을 모두 처리한다.

#### Entity에 많은 책임 부여

Entity가 대부분의 도메인 규칙과 외부 요청 검증까지 처리한다.

#### Service와 Entity의 책임 분리

Service는 하나의 유스케이스를 수행하고, Entity는 자신의 상태와 도메인 규칙을 보호한다.

### 결정

Service 계층은 하나의 유스케이스 흐름을 조율한다.  
Entity는 유스케이스 자체를 알지 못하며, 자신의 상태와 도메인 규칙을 보호한다.

#### Service 책임

- 사용자 요청 검증
- Repository 조회
- 존재 여부 검증
- ACTIVE 상태 검증
- 권한 검사
- 여러 도메인 객체의 협력 조율
- DTO 변환 및 반환

#### Entity 책임

- 자신의 상태 전이
- 자신의 불변식 보호
- 자기 자신에 대한 판단
- 의미 있는 도메인 메서드 제공

예시

```java
member.updateProfile(nickname, gender);
member.withdraw();
member.isAdmin();

board.update(title, content, category);
board.delete();
board.isDeleted();

comment.update(content);
comment.delete();
comment.canReply();
comment.isWrittenIn(boardId);
```

### 예외 처리 기준

Service에서 발생하는 예외는 유스케이스 실패를 의미한다.

예시

```text
MemberNotFoundException
BoardNotFoundException
CommentNotFoundException
LoginFailedException
AccessDeniedException
ReplyNotAllowedException
```

Entity에서 발생하는 예외는 객체 상태 위반 또는 잘못된 상태 전이 시도를 의미한다.

예시

```text
IllegalStateException
IllegalArgumentException
```

### 이유

Service는 외부 요청을 받아 하나의 기능을 완성하는 계층이다.

따라서 요청한 사용자가 유효한지, 대상 리소스가 존재하는지, 해당 사용자가 권한을 가지는지와 같은 유스케이스 수준 검증은  
Service에서 처리하는 것이 적절하다고 판단했다.

반면 Entity는 특정 요청 흐름이나 화면을 알 필요가 없다.  
Entity는 자신의 상태가 유효한지, 현재 상태에서 특정 행위를 수행할 수 있는지만 책임진다.

이렇게 분리하면 Service는 유스케이스 흐름을 표현하고, Entity는 도메인 객체로서 자신의 규칙을 보호할 수 있다.

### 결과

- 계층별 책임 명확화
- 유스케이스 흐름과 도메인 상태 전이 분리
- 도메인 객체의 불변식 보호
- Service가 도메인 객체와의 협력을 조율하는 구조 확립
- Member, Board, Comment 이후 기능에도 일관된 설계 기준 적용 가능

## AD-035. DTO 기반 계층 분리와 OSIV(false) 적용

### 배경

JPA Entity를 Controller나 View 계층까지 직접 전달하면, Presentation Layer가 영속성 계층의 모델에 의존하게 된다.  
또한 지연 로딩(Lazy Loading)이 View 렌더링 시점에 발생할 수 있어, 영속성 컨텍스트의 생명주기가 View 계층까지 확장되는 문제가 발생할 수 있다.  
Dev Board는 계층별 책임을 명확히 분리하고, 영속성 컨텍스트의 사용 범위를 Service 계층 중심으로 제한하고자 했다.

### 고려한 대안

#### Entity를 Controller/View까지 전달

Service가 Entity를 반환하고, Controller/View에서 필요한 값을 사용한다.

#### DTO로 변환하여 Controller/View에 전달

Service 계층에서 필요한 모든 데이터를 DTO로 변환하여 반환하고, Controller와 View는 DTO만 사용한다.

### 결정

OSIV(Open Session In View)는 false로 가져가고, Entity를 Controller/View 계층에 직접 노출시키지 않는다.  
Service 계층에서 필요한 데이터를 DTO로 변환하여 반환한다.  
Controller와 View는 DTO만 사용한다.

### 이유

DTO 기반 계층 분리의 1차 목적은 LazyInitializationException을 피하는 것이 아니라, 계층 간 책임을 분리하는 것이다.

Presentation Layer가 Entity에 직접 의존하면 다음과 같은 문제가 발생할 수 있다.

- View 요구사항 변경이 Entity 구조에 영향
- Entity 변경이 화면 출력 구조에 직접 영향
- 지연 로딩이 View 렌더링 시점에 발생
- 영속성 컨텍스트 사용 범위 불명확

따라서 필요한 연관 데이터는 Service 계층에서 조회하고 DTO로 변환한 뒤 Controller/View에 전달해야 한다.  
이 구조는 영속성 컨텍스트의 사용 범위를 Service 계층 안으로 제한하고, View 계층이 JPA Entity에 의존하지 않도록 만든다.

### 결과

- Presentation Layer와 Persistence Model 분리
- Entity의 외부 노출 방지
- 영속성 컨텍스트 사용 범위 명확화
- OSIV(false) 환경에서도 안전한 화면 렌더링 가능
- LazyInitializationException 예방
- View 요구사항에 맞는 응답 DTO 독립 설계 가능

#### 트레이드오프

- DTO 클래스 수 증가
- Service 계층에서 DTO 변환 코드 필요
- 화면별 응답 구조 별도 설계 필요

그러나 Dev Board는 명확한 계층 분리와 유지보수성을 우선하여, 
명시적인 DTO 변환 비용을 감수하더라도 Entity 외부 노출 방지와 영속성 컨텍스트 범위 제한을 선택했다.

# 2. 인증 및 사용자 식별

## AD-003. ACTIVE 회원 검증 책임을 Service 계층으로 집중

### 배경

초기 구현에서는 다음 계층들 모두 ACTIVE 회원 검증을 수행했다.

```text
LoginCheckInterceptor
LoginMemberIdArgumentResolver
Controller
Service
```

즉, 동일한 검증 로직이 여러 계층에 중복되어 존재했다.

### 문제

- 검증 로직 중복
- 책임 경계 불명확
- 정책 변경 시 수정 범위 증가

### 판단

ACTIVE 회원 여부는 인증 정책이 아니라, 비즈니스 정책에 가깝다.

### 결정

ACTIVE 회원 검증 책임을 Service 계층으로 집중시켰다.

각 계층의 역할을 다음처럼 분리했다.

- Interceptor
  - 로그인 여부 확인
- ArgumentResolver
  - 사용자 식별
- Service
  - ACTIVE 회원 검증
  - 비즈니스 규칙 처리

### 결과

- 인증 / 비즈니스 규칙 분리
- 검증 로직 중복 제거
- 책임 경계 명확화
- 정책 변경 시, 수정 범위 최소화

### 배경

초기 구현에서는 Controller마다 로그인 여부를 직접 검사했다.

### 문제

### 결과

- 유지보수성 향상

## AD-005. LoginMemberId ArgumentResolver 도입

### 배경

Controller에서 HttpSession을 직접 사용하면, 인증 정보 접근 코드가 반복된다.

### 결정

Controller에서 세션을 직접 다루지 않는다.  
로그인 사용자 식별은 ArgumentResolver를 통해 수행한다.

예시

```java
public String writeForm(@LoginMemberId Long memberId) {
}
```

### 추가 결정

로그인 검증을 통과한 요청에서 사용자 ID를 찾을 수 없는 경우는, 정상 흐름에서 발생할 수 없는 상황으로 판단했다.

따라서 해당 경우는 `IllegalStateException`을 발생시켜 시스템 오류로 간주한다.

즉, 이는 시스템 불변식 위반으로 간주한다.

### 결과

- Controller의 세션 의존성 제거
- Controller의 인증 관련 코드 제거
- 인증 정보 접근 방식 통일
- 시스템 불변식(Invariant) 보호

## AD-006. 로그인 후 원래 요청 페이지 복귀

### 배경

비로그인 사용자가 인증이 필요한 페이지를 접근하려 하면, 로그인 화면으로 이동한다.  
로그인 성공 후 원했던 페이지로 다시 이동하지 못하면 사용자 경험이 저하된다.

### 결정

로그인 페이지 이동 시, 원래 요청 URL을 포함시켜 전달한다.  
로그인 성공 후 요청 URL로 복귀시킨다.  
Query String을 포함하며, URL Encoding을 적용한다.

### 결과

- 사용자 경험 향상
- 인증 흐름 자연화

# 4. 데이터 관리 정책

## AD-008. Soft Delete 정책 채택

### 배경

데이터 물리 삭제 시, 추적이 어려워지고 연관 데이터 처리 문제가 발생한다.

특히 게시글, 댓글, 좋아요 등의 기능은 삭제 이후에도 관계를 유지할 필요가 있다.

### 고려한 대안

#### Hard Delete

실제 데이터를 DB에서 물리 삭제한다.

#### Soft Delete

상태값(status)만 변경한다.

### 결정

Soft Delete 정책을 채택했다.

적용 대상

- Member
- Board
- Comment

### 결과

- 데이터 보존
- 데이터 감사(Audit) 가능
- 회원 탈퇴 이후에도 작성 게시글 및 댓글 이력 유지
- 삭제 게시글 및 삭제 댓글의 표시 정책 확장 가능
- 향후 좋아요, 첨부파일 등 연관 도메인 확장에 유리

---

## AD-009. 탈퇴 회원 이메일 및 닉네임 재사용 금지

### 배경

Soft Delete 적용 시, 기존 회원 정보의 재사용 여부를 결정해야 했다.

### 결정

탈퇴 회원의 이메일과 닉네임의 재사용을 허용하지 않는다.

### 이유

- 사용자 식별 일관성 유지
- 데이터 추적 가능성 확보
- 운영 정책 단순화

### 결과

- 회원 이력 보존
- 동일 식별자 재사용 방지

---

## AD-010. Entity 캡슐화 정책

### 배경

Setter 기반 설계는 Entity 상태를 외부에서 자유롭게 변경할 수 있게 만든다.  
이로 인해, 데이터 변경 지점의 추적이 어려워지는 문제가 발생한다.

### 결정

Setter를 사용하지 않는다.  
상태 변경은 의미 있는 메서드를 통해서만 수행한다.

예시

```text
member.updateProfile(nickname, gender);
member.withdraw();

board.update(title, content, category);
board.delete();

comment.update(content);
comment.delete();
```

### 결과

- 무분별한 상태 변경 방지
- 도메인 규칙 보호
- 상태 전이 규칙 보호
- 객체지향적 모델링 강화

# 5. 게시판 설계

## AD-011. 게시판 페이징 직접 구현

### 배경

Spring Data JPA는 `Page`와 `Pageable`을 통해 페이징 기능을 편리하게 제공한다.

그러나 초기 구현 단계에서는 프레임워크 추상화에 바로 의존하기보다, 게시판 페이징에 필요한 계산 기준과 보정 정책을 직접 설계하고 검증하는 것이 더 적합하다고 판단했다.

특히 Dev Board에서는 다음 정책을 명시적으로 제어할 필요가 있었다.

- 전체 게시글 수 계산
- 전체 페이지 수 계산
- 페이지 블록 계산
- 이전/다음 페이지 이동 기준
- 비정상 페이지 요청에 대한 clamp 보정

### 결정

게시판 페이징을 직접 구현했다.

### 결정

게시글은 작성자만 수정할 수 있도록 결정했다.

### 이유

게시글 수정은 작성자가 작성한 내용과 의도를 변경하는 행위이다.

관리자의 역할은 서비스 운영에 있으며, 콘텐츠를 대신 수정하는 역할과는 구분되어야 한다고 판단했다.

### 결과

- 게시글 작성자의 의도 보존
- 운영 권한과 콘텐츠 소유권 분리
- 관리자와 작성자 역할 명확화

## AD-020. 권한 기반 UI 표시 정책

### 배경

게시글 상세 화면에서 수정 및 삭제 버튼의 노출 여부를 결정해야 했다.  
수정과 삭제는 서로 다른 권한 정책을 가지므로, 단순히 작성자 여부만으로는 버튼 노출을 결정할 수 없었다.

### 고려한 대안

#### Controller에서 권한 계산

Controller에서 `canEdit`, `canDelete` 값을 계산하여 View에 전달한다.

#### Service에서 권한 계산

BoardService에서 `canEdit()`, `canDelete()` 메서드를 제공하여 권한 여부를 반환한다.

#### Permission DTO 도입

수정, 삭제 등 화면에서 필요한 권한 정보를 하나의 DTO로 구성하여 View에 전달한다.

### 결정

현재 프로젝트에서는 Controller에서 `canEdit`와 `canDelete`를 계산하여 View에 전달하도록 결정했다.

### 이유

현재 권한 정보는 게시글 상세 화면에서만 사용되며, 필요한 정보도 `canEdit`, `canDelete` 두 가지로 단순하다.  
이러한 상황에서 UI 표시만을 위한 별도의 Service 메서드나, Permission DTO를 도입하는 것은 현재 프로젝트 규모에 비해, 과도한 설계라고 판단했다.  
또한, 현재 구조에서 별도의 Service 메서드를 사용할 경우, 이미 조회한 게시글 정보를 활용하지 못하고 동일 게시글에 대한 재조회가 발생할 수 있다고 판단했다.

특히, 수정 및 삭제 권한에 대한 실제 검증은 `BoardService`에서 수행하므로, Controller에서는 화면 표시를 위한 권한 정보만 계산하도록 역할을 분리했다.

### 결과

- View는 전달받은 권한 정보만 이용하여 버튼 노출 여부 결정
- UI 표시와 실제 권한 검증의 책임 분리
- 현재 프로젝트 규모에 적합한 단순한 구조 유지
- 권한 정책이 복잡해질 경우, Permission DTO 또는 별도 권한 객체 도입 가능

## AD-022. 게시글 조회수 증가 정책

### 배경

게시글 조회수는 게시글의 관심도와 활동량을 나타내는 대표적인 지표이다.

따라서, 어떤 행위를 게시글 조회로 간주하여 조회수를 증가시킬 것인지와 중복 조회를 어느 수준까지 허용할 것인지에 대한 정책을 결정해야 했다.  
또한 회원과 비회원, 작성자와 관리자 등 사용자 유형에 따라 서로 다른 정책을 적용할지 여부도 함께 검토했다.

### 고려한 대안

#### 1. 조회 인정 기준

##### 게시글 조회 요청을 조회로 간주

게시글 조회 요청이 발생한 시점을 조회로 간주하여 조회수를 증가시킨다.

##### 게시글 상세 화면 진입을 조회로 간주

사용자가 게시글 내용을 실제로 확인하기 위해 상세 화면에 진입한 경우를 조회로 간주하여 조회수를 증가시킨다.

---

#### 2. 중복 조회 정책

##### 중복 조회 모두 허용

게시글을 조회할 때마다 조회수를 증가시킨다.

##### 일정 기간 동안 중복 조회 제한

동일한 사용 환경에서는 일정 기간 동안 동일 게시글의 조회수를 한 번만 증가시킨다.

---

#### 3. 작성자 조회 정책

##### 작성자는 조회수 증가 제외

작성자가 자신의 게시글을 조회하면, 조회수를 증가시키지 않는다.

##### 작성자도 조회수 증가

작성자의 조회도 일반적인 조회로 간주하여 조회수를 증가시킨다.

---

#### 4. 관리자 조회 정책

##### 관리자는 조회수 증가 제외

관리자의 조회는 운영 목적으로 간주하여 조회수를 증가시키지 않는다.

##### 관리자도 조회수 증가

관리자의 조회도 일반적인 조회로 간주하여 조회수를 증가시킨다.

---

### 결정

- 게시글 상세 화면 진입 시 조회수를 증가시킨다.
- 동일한 사용 환경에서는 24시간 동안 동일 게시글의 조회수를 한 번만 증가시킨다.
- 회원과 비회원 모두 동일한 정책을 적용한다.
- 작성자 및 관리자의 조회도 조회수에 포함한다.
- 삭제 게시글은 조회수를 증가시키지 않는다.

### 이유

게시글 조회 요청만으로는 사용자가 게시글 내용을 실제로 확인했다고 보기 어렵다고 판단하여, 게시글 상세 화면에 진입한 경우를 조회로 간주했다.  
또한, 조회할 때마다 조회수를 증가시키는 방식은 새로고침이나 반복 조회만으로 조회수가 쉽게 증가하여 실제 관심도를 반영하기 어렵다고 판단했다.  
작성자와 관리자 역시 게시글을 실제로 확인하는 사용자이므로, 별도의 예외를 두기보다는 동일한 정책을 적용하는 것이 정책의 일관성과 구현의 단순성 측면에서 적절하다고 판단했다.

삭제 게시글은 일반적인 게시글 조회 대상이 아니므로 조회수를 증가시키지 않도록 결정했다.  
중복 조회 제한 기간은 일반적인 게시판 서비스에서 널리 사용하는 정책을 참고하여 24시간으로 결정했다.

### 결과

- 실제 열람을 기준으로 한 조회수 정책 확립
- 반복 조회에 의한 조회수 왜곡 완화
- 회원 유형과 관계없는 일관된 조회수 정책 적용
- 단순하고 예측 가능한 조회수 증가 정책 유지

## AD-023. Cookie 기반 조회수 중복 증가 방지

### 배경

동일한 사용 환경에서 동일 게시글이 여러 번 조회될 경우, 일정 기간 동안 조회수가 중복 증가되지 않도록 구현할 필요가 있었다.  
이를 위해 조회 이력을 어디에서 관리할 것인지와, 애플리케이션 계층 간의 책임을 어떻게 분리할 것인지에 대한 설계를 검토했다.

---

### 고려한 대안

#### 1. 조회 이력 저장 위치

##### Cookie 기반 관리

- 조회한 게시글 ID를 브라우저의 Cookie에 저장하여 중복 조회 여부를 판단한다.

##### Session 기반 관리

- 조회한 게시글 ID를 서버의 Session에 저장하여 중복 조회 여부를 판단한다.

##### DB 또는 Redis 기반 관리

- 조회 이력을 서버에 저장하여 중복 조회 여부를 판단한다.

---

#### 2. Cookie 저장 방식

##### 게시글마다 별도의 Cookie 생성

- 게시글마다 하나의 Cookie를 생성하여 조회 여부를 관리한다.

##### 하나의 Cookie에 여러 게시글 ID 저장

- 하나의 Cookie에 조회한 게시글 ID를 함께 저장하여 조회 여부를 관리한다.

---

#### 3. 계층 간 책임

##### Controller에서 Cookie 처리 / Service에서 조회수 증가

- Controller는 HTTP 요청과 Cookie를 처리하고, Service는 조회수 증가만 담당한다.

##### Service에서 Cookie까지 함께 처리

- Service가 조회수 증가와 Cookie 처리까지 함께 담당한다.

---

### 결정

- 조회 이력은 Cookie 기반으로 관리한다.
- 하나의 Cookie에 여러 게시글 ID를 저장한다.
- Cookie 처리는 Controller에서 담당하고, Service는 조회수 증가만 담당한다.

---

### 이유

#### Cookie 기반 조회 이력 관리

Cookie는 별도의 서버 저장소 없이도, 회원과 비회원 모두 동일한 정책을 적용할 수 있다.  
또한 구현이 단순하고 일반적인 게시판 서비스에서도 널리 사용되는 방식이다.  
Session은 서버가 상태를 유지해야 하며 회원과 비회원 모두에게 동일한 정책을 적용하기에는 적합하지 않다고 판단했다.  
DB 또는 Redis를 이용한 방식은 가장 정확하게 중복 조회를 관리할 수 있지만, 현재 프로젝트 규모와 요구사항을 고려했을 때 과도한 설계라고 판단했다.

단, 사용자가 Cookie를 삭제하거나 다른 브라우저를 사용하는 경우에는 중복 조회를 완전히 방지할 수 없다는 한계가 있다.

그러나 일반적인 사용 환경에서는 반복 새로고침 등에 의한 조회수 증가를 효과적으로 방지할 수 있으며, 현재 프로젝트의 규모와 목적을 고려하여 해당 방식을 채택했다.

#### 하나의 Cookie에 여러 게시글 ID 저장

게시글마다 별도의 Cookie를 생성하면, 게시글 수가 증가할수록 Cookie 수도 함께 증가한다.

반면, 하나의 Cookie에 여러 게시글 ID를 저장하는 방식이 관리 측면에서 더 적절하다고 판단했다.

#### Controller와 Service의 책임 분리

Cookie는 HTTP 계층의 정보이므로 Controller에서 처리하고, Service는 조회수 증가라는 비즈니스 로직만 담당하도록 역할을 분리했다.

---

### 결과

- 회원과 비회원 모두 동일한 조회수 정책 적용
- 서버 상태를 유지하지 않는 단순한 조회 이력 관리
- HTTP 처리와 비즈니스 로직의 책임 분리
- 프로젝트 규모에 적합한 조회수 중복 증가 방지 정책 적용

---

## AD-024. 공지사항 표시 정책

### 배경

공지사항 기능을 구현하면서, 게시글 목록에서 공지사항을 어떻게 표현할 것인지에 대한 정책을 결정해야 했다.  
초기에는 공지사항을 항상 목록 상단에 고정하는 방안을 고려했지만, 공지사항의 역할과 게시글 목록의 사용자 경험을 함께 검토할 필요가 있었다.

### 고려한 대안

#### 공지사항 최상단 고정

공지사항을 게시글 목록에서 항상 최상단에 노출한다.

#### 공지사항 시각적 강조

일반 게시글과 동일한 정렬 정책을 유지하되, `[공지]` 라벨과 강조 색상을 통해 시각적으로 구분한다.

### 결정

공지사항과 일반 게시글의 정렬 정책을 동일하게 가져가되, `[공지]` 라벨과 강조 색상을 통해 시각적으로 구분하도록 결정했다.

### 이유

공지사항(NOTICE)은 게시글의 성격을 나타내는 **카테고리**이며, 게시글을 항상 목록 상단에 노출하는 **운영 정책**과는 서로 다른 개념이라고 판단했다.

공지사항을 항상 최상단에 고정할 경우, 다음과 같은 문제가 발생할 수 있다.

- 공지사항이 많아질수록 일반 게시글이 뒤로 밀려, 사용자 경험이 저하될 수 있다.
- Soft Delete 정책을 적용하는 현재 구조에서는 삭제된 공지사항까지 상단에 유지되는 문제가 발생한다.
- 공지사항 개수 제한, 고정 해제, 고정 기간 등 추가적인 운영 정책이 필요하게 된다.

현재 프로젝트에서는 이러한 운영 정책까지 포함하기보다, 공지사항은 카테고리로만 관리하고, 표시 방식은 시각적 강조에 한정하는 것이 프로젝트 규모와 목적에 적합하다고 판단했다.

향후 운영 기능이 필요해질 경우, 공지사항(NOTICE)과 고정(PINNED) 정책을 별도의 개념으로 분리하는 방향을 고려한다.

### 결과

- 일반 게시글과 동일한 정렬 정책 유지
- `[공지]` 라벨과 강조 색상을 통해 게시글 목록에서 시각적으로 구분
- 카테고리와 운영 정책 분리를 통한 도메인 모델의 일관성 유지
- 향후 운영 정책 필요 시, 별도의 고정(PINNED) 정책으로 확장 가능하도록 설계 방향 유지

# 6. 댓글 설계

## AD-025. Comment Soft Delete 정책

### 배경

댓글은 게시글과 함께 커뮤니티의 대화 흐름을 구성하는 데이터이다.  
댓글을 물리 삭제할 경우, 대댓글이 함께 존재하는 상황에서 댓글의 계층 구조와 대화 맥락이 끊어질 수 있다.  
또한 회원 탈퇴, 게시글 삭제, 부모 댓글 삭제가 발생했을 때, 이와 연관된 댓글과 대댓글에도 삭제 상태를 전파할 것인지 결정할 필요가 있었다.

또한 부모 댓글과 대댓글은 서로 다른 회원이 작성할 수 있으므로, 부모 댓글 작성자의 삭제 행위가 다른 회원이 작성한 대댓글의 상태에 미치는 범위도 결정해야 했다.

### 고려한 대안

#### 댓글 삭제 방식

##### Hard Delete

댓글 삭제 시 해당 댓글 데이터를 DB에서 물리적으로 제거한다.  
대댓글이 존재하는 부모 댓글 삭제 시, 대댓글과의 연결 관계를 별도로 처리한다.

##### Soft Delete

댓글 데이터를 DB에서 제거하지 않고, 해당 댓글의 상태값만 `DELETED`로 변경한다.  
삭제된 댓글은 목록에서 유지하되, 기존 본문 대신 `삭제된 댓글입니다.`라는 문구를 표시한다.

#### 상위 데이터 삭제 시, 삭제 상태 전파 여부

##### 삭제 상태 전파

회원, 게시글 또는 부모 댓글이 `DELETED` 상태로 변경되면, 이와 연관된 댓글 및 대댓글의 상태도 함께 `DELETED`로 변경한다.

##### 독립적인 상태 관리

회원, 게시글 또는 부모 댓글이 `DELETED` 상태로 변경되더라도, 이와 연관된 댓글 및 대댓글의 상태는 변경하지 않는다.  
각 댓글과 대댓글은 자신의 상태를 독립적으로 유지한다.

### 결정

#### Comment에 Soft Delete를 적용한다.

댓글 삭제 시 데이터를 DB에서 물리적으로 제거하지 않고, 해당 댓글의 상태값만 `DELETED`로 변경한다.  
삭제한 댓글은 목록에서 제거하지 않으며, 기존 본문 대신 `삭제된 댓글입니다.`라는 문구를 표시한다.

#### 각 댓글과 대댓글은 자신의 상태를 독립적으로 유지한다.

회원이 탈퇴하거나 게시글이 삭제되더라도, 해당 회원이 작성했거나 해당 게시글에 속한 댓글의 상태는 변경하지 않는다.  
부모 댓글이 삭제되더라도, 해당 댓글에 작성된 대댓글의 상태는 변경하지 않는다.

즉, ACTIVE 상태인 대댓글은 부모 댓글이 삭제된 이후에도 독립적으로 수정하거나 삭제할 수 있다.  
삭제된 댓글은 수정하거나 다시 삭제할 수 없다.

### 이유

댓글을 물리적으로 삭제하면, 대댓글이 존재하는 경우 댓글의 계층 구조와 대화 맥락을 유지하기 어렵다.  
Soft Delete를 적용하면 삭제된 댓글의 본문은 노출하지 않으면서도, 댓글과 대댓글의 연결 관계 및 전체적인 대화 흐름을 보존할 수 있다.  
회원 탈퇴나 게시글 삭제 시 연관 댓글의 상태를 함께 변경하지 않음으로써, 상위 데이터의 상태 변경과 댓글 자체의 삭제 상태를 구분할 수 있다.

또한 부모 댓글의 삭제 상태를 대댓글에 전파하지 않음으로써, 부모 댓글 작성자의 삭제 행위가 다른 회원이 작성한 대댓글의 상태에 영향을 주지 않도록 했다.  
삭제된 댓글은 더 이상 변경할 수 없는 상태로 간주하여, 수정하거나 다시 삭제하지 못하도록 제한한다.  
Member와 Board에 적용된 기존 Soft Delete 방식과 동일하게 Comment도 데이터를 보존하는 방식으로 관리함으로써, 프로젝트 전체의 삭제 정책을 일관되게 유지할 수 있다.

### 결과

- 댓글 데이터와 삭제 이력 보존
- 삭제된 댓글의 본문 비노출
- 댓글과 대댓글의 계층 구조 및 대화 맥락 유지
- 회원 탈퇴 시 해당 회원이 작성한 댓글과 대댓글의 상태 유지
- 게시글 삭제 시 해당 게시글에 속한 댓글과 대댓글의 상태 유지
- 부모 댓글 삭제 시 대댓글로 삭제 상태가 전파되는 것 방지
- ACTIVE 대댓글의 독립적인 수정·삭제 보장
- 삭제된 댓글의 수정 및 중복 삭제 방지
- Member, Board, Comment의 Soft Delete 정책 일관성 확보

## AD-026. 대댓글 1단계 제한 정책

### 배경

댓글 기능을 구현하면서 대댓글의 깊이를 어디까지 허용할 것인지 결정해야 했다.  
대댓글 깊이를 제한하지 않으면 복잡한 트리 구조가 필요해지고, 화면 렌더링과 API 응답 구조도 함께 복잡해진다.

### 고려한 대안

#### 무제한 대댓글 허용

대댓글에 다시 대댓글을 작성할 수 있도록 허용한다.

#### 1단계 대댓글만 허용

최상위 댓글에만 대댓글을 작성할 수 있도록 제한한다.

### 결정

대댓글은 1단계까지만 허용한다.

즉, 댓글에는 대댓글을 작성할 수 있지만, 대댓글에는 다시 대댓글을 작성할 수 없다.

### 이유

현재 프로젝트는 커뮤니티 게시판의 핵심 기능을 안정적으로 구현하고, 구조를 단순하고 유지보수 가능하게 설계하는 데 초점을 둔다.

무제한 대댓글을 허용하면 다음과 같은 복잡도가 증가한다.

- 트리 구조 조립
- 재귀 렌더링
- 들여쓰기 깊이 처리
- 응답 DTO 구조 복잡화
- JavaScript 렌더링 복잡화

현재 요구사항에서는 1단계 대댓글만으로도 일반적인 게시판 댓글 UX를 충분히 제공할 수 있다고 판단했다.

### 결과

- 댓글 구조 단순화
- 조회 및 렌더링 로직 단순화
- 댓글 API 응답 구조 단순화
- 향후 필요 시 다단계 댓글 구조로 확장 가능

## AD-027. 삭제된 댓글에 대댓글 작성 허용

### 배경

댓글 삭제 시 해당 댓글에 대한 대댓글 작성을 허용할지 여부를 결정해야 했다.  
삭제된 댓글은 본문이 노출되지 않지만, 이미 대댓글이 존재하거나 이후 토론이 이어질 수 있는 구조에서는 대화 흐름 유지 여부가 중요하다.

### 고려한 대안

#### 삭제된 댓글에는 대댓글 작성 불가

삭제된 댓글을 더 이상 상호작용할 수 없는 상태로 간주한다.

#### 삭제된 댓글에도 대댓글 작성 허용

삭제된 댓글의 본문은 숨기되, 해당 댓글 아래의 대화 흐름은 유지한다.

### 결정

삭제된 댓글에도 대댓글 작성을 허용한다.  
단, 삭제된 댓글의 본문은 `삭제된 댓글입니다.` 형태로 표시한다.

### 이유

Comment는 게시글 아래에서 이루어지는 토론의 일부이다.  
댓글 삭제는 작성자가 작성한 내용을 더 이상 노출하지 않겠다는 의미이지, 토론 자체를 종료한다는 의미는 아니라고 판단했다.  
삭제된 댓글에 이미 대댓글이 존재할 수 있으며, 댓글이 삭제되었다는 이유만으로 대화 흐름 전체를 차단하는 것은 사용자 경험을 해칠 수 있다고 판단했다.

따라서 삭제된 댓글의 본문은 `삭제된 댓글입니다.` 형태로 숨기되, 해당 댓글 아래의 토론은 계속 이어질 수 있도록 대댓글 작성을 허용한다.

### 결과

- 삭제 댓글의 본문 비노출
- 대댓글을 통한 대화 흐름 유지
- 댓글 삭제 의도와 토론 지속성의 균형 확보
- 토론형 게시판 UX 확보

## AD-028. 댓글 조회 결과를 Flat List로 제공

### 배경

댓글과 대댓글을 화면에 표시하기 위해 응답 구조를 결정해야 했다.  
댓글은 계층 구조를 가지지만, 현재 정책상 대댓글은 1단계까지만 허용한다.

### 고려한 대안

#### Tree DTO

부모 댓글이 자식 댓글 목록을 가지는 구조로 응답한다.

#### Flat DTO List

부모 댓글과 대댓글을 화면 출력 순서에 맞춘 단일 리스트로 응답한다.

### 결정

댓글 조회 결과는 Flat List 형태로 제공한다.  
Service에서는 부모 댓글 아래에 대댓글이 배치되도록 순서를 구성한다.  
Controller 또는 JavaScript는 전달받은 순서대로 렌더링한다.

### 이유

현재 대댓글은 1단계까지만 허용되므로, Tree DTO를 도입할 만큼 구조가 복잡하지 않다고 판단했다.

또한, Flat List를 사용하면 다음과 같은 장점이 있다.

- 응답 구조 단순화
- JavaScript 렌더링 단순화
- 화면 출력 순서 예측 가능
- 댓글과 대댓글을 동일한 DTO로 처리 가능

### 결과

- 댓글 조회 API 응답 구조 단순화
- View 및 JavaScript 렌더링 부담 감소
- 현재 프로젝트 규모에 적합한 구조 유지
- 향후 다단계 댓글 도입 시 Tree 구조 재검토 가능

## AD-029. 댓글 작성 대상 정책

### 배경

댓글 작성 기능을 구현하면서, 어떤 상태의 게시글에 댓글 작성을 허용할지 결정해야 했다.  
현재 게시글은 Soft Delete 정책을 사용하므로, 삭제된 게시글도 DB에는 남아 있다.

따라서 단순히 게시글이 존재하는지만 확인할 경우, 삭제된 게시글에도 새로운 댓글이나 대댓글이 작성될 수 있다.

### 고려한 대안

#### 존재하는 게시글이면 댓글 작성 허용

게시글이 DB에 존재하면, 상태와 관계없이 댓글 작성을 허용한다.

#### ACTIVE 게시글에만 댓글 작성 허용

게시글 상태가 `ACTIVE`인 경우에만 댓글 작성을 허용한다.

### 결정

댓글은 `ACTIVE` 게시글에만 작성할 수 있도록 결정했다.  
삭제된 게시글에는 댓글과 대댓글을 작성할 수 없다.  
삭제 게시글 상세 조회를 향후 허용하더라도, 삭제된 게시글은 읽기 전용(Read Only) 상태로 유지한다.

### 이유

게시글은 댓글과 대댓글이 이루어지는 토론 공간이다.  
게시글이 삭제되었다는 것은 해당 토론 공간에 대한 새로운 상호작용을 종료한다는 의미로 보았다.  
만약 삭제된 게시글에 댓글, 대댓글, 좋아요와 같은 새로운 활동이 발생하면 게시글 삭제의 의미가 약해질 수 있다.

반면 Comment 삭제는 작성자의 내용을 숨기는 것이며, 이미 형성된 토론 흐름을 반드시 종료한다는 의미는 아니다.

따라서 Board 삭제와 Comment 삭제는 서로 다른 정책을 적용한다.

- Board 삭제: 새로운 상호작용 종료
- Comment 삭제: 작성자의 내용 비노출, 토론 흐름 유지

### 결과

- 삭제 게시글에 새로운 댓글 작성 방지
- 게시글 삭제 의미 보존
- 삭제 게시글의 향후 상세 조회 허용 여부와 댓글 작성 정책 분리
- Board는 토론 공간, Comment는 토론 내용이라는 역할 명확화

## AD-030. 댓글 기능 AJAX 도입

### 배경

댓글 조회·작성·수정·삭제는 모두 게시글 상세 화면의 댓글 영역에서 이루어진다.  
댓글 기능을 SSR 방식으로 처리하면 각 작업을 수행할 때마다 게시글 상세 화면 전체를 다시 요청하고 재렌더링해야 한다.

이 경우 사용자의 스크롤 위치와 댓글 입력 상태가 초기화될 수 있으며, 댓글 영역의 일부만 변경되는데도 전체 페이지가 새로고침되어 사용자 경험이 저하되는 문제가 발생한다.

특히 대댓글 작성과 댓글 수정은 사용자가 댓글 영역 안에서 연속적으로 수행하는 작업이므로, 현재 화면의 흐름을 유지하면서 결과를 반영할 방법이 필요했다.

### 고려한 대안

#### SSR + PRG 방식

댓글 작성·수정·삭제 요청을 일반 HTML Form으로 전송하고, 처리 완료 후 게시글 상세 화면으로 Redirect한다.  
댓글 목록은 게시글 상세 화면을 렌더링할 때 함께 조회한다.

#### AJAX 방식

JavaScript에서 댓글 관련 API를 비동기로 호출한다.  
게시글 상세 화면은 그대로 유지하고, 댓글 영역만 최신 데이터로 재렌더링한다.

### 결정

댓글 조회·작성·수정·삭제에 AJAX 방식을 적용한다.  
게시글 상세 화면 자체는 Thymeleaf로 렌더링하고, 댓글 영역만 JavaScript가 댓글 API를 호출하여 별도로 구성한다.

댓글 관련 작업은 다음과 같이 처리한다.

- 게시글 상세 화면 진입 후 댓글 목록 비동기 조회
- 댓글 및 대댓글 비동기 작성
- 댓글 및 대댓글 비동기 수정
- 댓글 및 대댓글 비동기 삭제
- 각 작업 성공 후 댓글 영역 갱신

따라서 댓글 관련 작업이 이루어지더라도, 게시글 상세 화면 전체를 새로고침하지 않는다.

### 이유

댓글 기능은 게시글 상세 화면 전체가 아니라, 댓글 영역의 데이터와 UI만 변경되는 특성이 있다.

따라서 댓글 작업마다 전체 페이지를 다시 렌더링하는 것보다, 변경이 필요한 댓글 영역만 갱신하는 방식이 더 적합하다고 판단했다.  
AJAX를 적용하면 사용자가 머물고 있는 게시글 상세 화면과 스크롤 흐름을 유지하면서 댓글 작성·수정·삭제 결과를 반영할 수 있다.  
또한 댓글 조회와 변경 작업을 JSON API로 통일함으로써, 댓글 UI와 서버의 댓글 처리 책임을 명확하게 분리할 수 있다.

게시글 상세 화면은 Thymeleaf 기반 SSR 방식을 유지하고, 상호작용이 빈번한 댓글 영역에만 AJAX를 적용하여, 프로젝트 전체를 SPA(Single Page Application) 구조로 변경하지 않고도 필요한 사용자 경험을 개선할 수 있다.

### 결과

- 댓글 조회·작성·수정·삭제 시 전체 페이지 새로고침 방지
- 게시글 상세 화면과 사용자의 스크롤 흐름 유지
- 댓글 및 대댓글 작성·수정·삭제 UX 개선
- 댓글 영역의 독립적인 갱신 가능
- 댓글 관련 요청과 응답을 JSON API 방식으로 통일
- Thymeleaf 기반 SSR과 AJAX를 함께 사용하는 구조 확립
- 향후 댓글 기능 확장에 활용할 수 있는 비동기 처리 기반 확보

## AD-031. CommentApiController 분리

### 배경

게시글 상세 화면은 Thymeleaf 기반 HTML View로 렌더링한다.

반면 댓글 조회·작성·수정·삭제는 AJAX 기반으로 처리하므로, 댓글 데이터를 주고받을 수 있는 별도의 API가 필요하다.  
하나의 Controller 안에서 HTML View 반환과 JSON API 처리를 함께 담당할 경우, Controller의 역할이 혼재될 수 있다.

### 고려한 대안

#### BoardController에서 댓글 API까지 처리

게시글 상세 화면과 댓글 관련 API를 하나의 Controller에서 함께 처리한다.

#### CommentApiController 분리

게시글 상세 화면은 `BoardController`가 담당하고, 댓글 관련 API는 `CommentApiController`가 담당한다.

### 결정

`CommentApiController`를 별도로 분리한다.

각 Controller의 책임은 다음과 같이 구분한다.

```text
BoardController
 → 게시글 관련 웹 요청 및 HTML View 처리

CommentApiController
 → 댓글 및 대댓글 조회·작성·수정·삭제 API 처리
```

댓글 API는 다음 경로를 사용한다.

```text
GET    /boards/{boardId}/comments
POST   /boards/{boardId}/comments
PATCH  /comments/{commentId}
DELETE /comments/{commentId}
```

게시글별 댓글 목록 조회와 댓글 작성은 `boardId`를 기준으로 처리한다.  
댓글 수정과 삭제는 `commentId`만으로 대상을 식별할 수 있으므로, 경로에 `boardId`를 포함하지 않는다.

### 이유

게시글 상세 화면과 댓글 API는 같은 화면에서 사용되지만, 반환 형식과 담당하는 책임이 다르다.  
`BoardController`는 게시글 관련 웹 요청과 HTML View 처리에 집중하고, `CommentApiController`는 댓글 데이터에 대한 API 요청 처리에 집중하도록 분리함으로써 각 Controller의 책임을 명확히 유지할 수 있다.  
또한 댓글 기능을 별도의 API Controller로 분리하면, 댓글 조회·작성·수정·삭제 기능을 동일한 구조 안에서 관리할 수 있다.

수정과 삭제 경로에서는 댓글 ID만으로 대상 댓글을 식별할 수 있고, 연관 참조를 통해 소속 게시글을 확인할 수 있으므로, 불필요한 `boardId`를 경로에 중복으로 포함하지 않는다.

### 결과

- HTML Controller와 API Controller의 책임 분리
- 각 Controller의 응답 형식과 역할 명확화
- 댓글 조회·작성·수정·삭제 API의 일관된 관리
- 댓글 수정·삭제 경로에서 불필요한 `boardId` 제거
- AJAX 기반 댓글 기능의 확장과 유지보수 용이성 확보

## AD-032. 댓글 변경 성공 후 전체 댓글 목록 재조회

### 배경

댓글 변경 작업(작성·수정·삭제) 성공 후, 변경 내용을 화면에 반영하는 방식이 필요했다.  
댓글 작성 시에는 새로운 댓글을 정렬 정책에 맞는 위치에 배치해야 하며, 특히 대댓글은 해당 부모 댓글 아래의 올바른 위치에 표시해야 한다.  
댓글 수정 시에는 변경된 본문을 반영해야 하고, 댓글 삭제 시에는 댓글을 목록에서 제거하지 않고 기존 본문 대신 `삭제된 댓글입니다.`라는 문구를 표시해야 한다.

이러한 변경 결과를 클라이언트에서 개별적으로 처리할지, 서버로부터 전체 댓글 목록을 다시 조회할지 결정해야 했다.

### 고려한 대안

#### 변경된 댓글만 화면에 반영

댓글 작성 시 API는 생성된 댓글 정보를 반환하고, JavaScript는 해당 댓글을 적절한 위치에 추가한다.  
댓글 수정 시 API는 변경된 댓글 정보를 반환하고, JavaScript는 해당 댓글의 본문만 변경한다.  
댓글 삭제 시 JavaScript가 해당 댓글을 삭제 상태의 UI로 직접 변경한다.

#### 전체 댓글 목록 재조회

댓글 작성·수정·삭제 성공 후 댓글 목록 API를 다시 호출한다.  
클라이언트는 서버가 제공한 최신 댓글 목록을 기준으로 댓글 영역 전체를 다시 렌더링한다.

### 결정

댓글 작성·수정·삭제 후 전체 댓글 목록을 재조회한다.

각 변경 API의 성공 응답은 다음과 같이 처리한다.

```text
POST    /boards/{boardId}/comments → 201 Created
PATCH   /comments/{commentId}      → 204 No Content
DELETE  /comments/{commentId}      → 204 No Content
```

클라이언트는 각 요청이 성공하면 `GET /boards/{boardId}/comments`를 다시 호출하고, 응답받은 전체 댓글 목록을 기준으로 댓글 영역을 갱신한다.

### 이유

전체 댓글 목록 재조회 방식은 구현이 단순하지만 댓글 변경 작업이 발생할 때마다 매번 댓글 목록 전체를 다시 가져와야 하는 비용이 든다.

그러나 현재 프로젝트에서는 하나의 게시글에 매우 많은 댓글이 누적되는 상황을 우선적인 요구사항으로 두지 않았다.

따라서 현재 단계에서는 변경된 댓글만 클라이언트에서 직접 처리하는 것보다, 서버가 제공한 최신 댓글 목록과 정렬 및 대댓글 배치 결과를 그대로 반영하는 방식의 단순성과 일관성을 우선했다.

특히 변경된 댓글만 화면에 반영하는 방식은 JavaScript가 작업별로 다음 내용을 직접 처리해야 한다.

- 새 댓글과 대댓글의 삽입 위치 계산
- 수정된 댓글 본문 교체
- 삭제된 댓글의 본문과 UI 변경
- 삭제된 댓글의 수정·삭제 버튼 제거
- 댓글 정렬 및 대댓글 배치 정책 유지

이 경우 서버의 댓글 정책과 동일한 화면 처리 로직이 클라이언트에도 중복될 수 있다.

반면 전체 댓글 목록을 재조회하면, 클라이언트는 서버가 제공한 최신 상태를 그대로 렌더링하면 된다.  
댓글과 대댓글의 정렬 및 배치 순서는 서버가 결정하며, 클라이언트는 서버가 제공한 목록의 순서대로 댓글 영역을 렌더링한다.

이를 통해 댓글의 정렬과 대댓글 배치, 삭제 댓글 표시 및 작업 가능 여부를 모든 변경 작업에서 일관되게 반영할 수 있다.

향후 댓글 수가 많아지거나 성능 문제가 확인되면, 변경된 댓글만 화면에 반영하는 방식이나 댓글 페이징 도입을 검토한다.

### 결과

- 댓글 작성·수정·삭제 후 화면 상태의 일관성 확보
- 댓글과 대댓글의 정렬 및 배치 순서 결정 책임을 서버에 일원화
- 삭제 댓글 표시 정책의 일관된 반영
- JavaScript의 작업별 DOM 변경 및 상태 관리 부담 감소
- 변경 API가 응답 본문 없이 상태 코드만 반환할 수 있는 구조 확립
- 댓글 목록 전체를 재조회하는 추가 비용 발생
- 향후 성능 문제 발생 시 부분 갱신 또는 댓글 페이징 검토 가능

## AD-033. API Validation 실패 응답 처리

### 배경

댓글 작성과 수정 API는 JSON 요청을 받는다.  
HTML Form 기반 요청에서는 validation 실패 시 오류 정보와 함께 HTML View를 다시 렌더링할 수 있다.

반면 AJAX 기반 API 요청에서는 클라이언트가 오류를 식별하고 화면에 표시할 수 있도록 validation 실패 결과를 JSON 형식으로 반환해야 한다.

댓글 작성과 수정 요청의 `content`에는 다음 validation을 적용한다.

- 공백을 포함한 빈 내용 입력 제한
- 최대 2,000자 길이 제한

validation 실패 응답을 Spring MVC의 기본 처리에 맡길지, 각 Controller에서 직접 구성할지, 또는 전역 예외 처리 구조를 도입할지를 결정할 필요가 있었다.

### 고려한 대안

#### Spring MVC 기본 예외 처리에 위임

`@Valid @RequestBody` validation 실패 시 Spring MVC의 기본 오류 응답을 사용한다.  
별도의 처리 코드를 작성하지 않아도 되지만, 클라이언트가 사용하기 위한 오류 응답 형식과 메시지를 직접 제어하기 어렵다.

#### Controller에서 BindingResult 처리

Controller 메서드에서 `BindingResult`를 받아 validation 실패 응답을 직접 구성한다.  
각 API에서 처리 코드가 필요하지만, 현재 기능에 필요한 오류 응답을 명시적으로 구성할 수 있다.

#### 전역 API 예외 처리 도입

`@RestControllerAdvice`를 도입하여 API validation 예외를 공통 처리한다.  
오류 응답을 일관되게 관리할 수 있지만, 현재 API 규모에 비해 별도의 공통 응답 구조가 필요하다.

### 결정

현재 단계에서는 `CommentApiController`에서 `BindingResult`를 사용하여 validation 실패 응답을 직접 처리한다.

댓글 작성과 수정 요청에서 validation 오류가 발생하면 서비스를 호출하지 않고 다음 형식의 응답을 반환한다.

```text
HTTP 400 Bad Request
Content-Type: application/json

{
    "message": "validation 오류 메시지"
}
```

`content` 필드에 등록된 오류가 있으면, DTO의 validation 메시지를 응답에 사용한다.  
사용할 수 있는 필드 오류 메시지가 없으면, `입력값이 올바르지 않습니다.`라는 기본 메시지를 반환한다.  
댓글 작성과 수정에 공통으로 필요한 오류 메시지 추출은 `CommentApiController`의 별도 메서드로 분리하여 사용한다.

클라이언트는 validation 실패로 `400 Bad Request` 응답을 받으면, JSON 응답의 `message`를 읽어 해당 댓글 작성·수정 Form의 오류 영역에 표시한다.

향후 validation을 적용하는 API가 여러 Controller로 확장되어 동일한 처리 코드가 반복되면, `@RestControllerAdvice` 기반의 전역 API 예외 처리 구조로 전환한다.

### 이유

현재 validation이 필요한 JSON API는 댓글 작성과 수정 기능뿐이며, 모두 하나의 `CommentApiController` 안에서 처리하고 있다.  
두 요청은 동일한 `content` 필드를 검증하고, 동일한 형태의 오류 응답을 사용하므로, 현재 단계에서는 Controller 내부의 공통 메서드만으로도 중복을 제한하면서 필요한 응답 형식을 명확하게 제어할 수 있다.

또한 `BindingResult`를 통해 validation 실패를 Controller에서 직접 확인하면, 잘못된 요청이 서비스 계층으로 전달되는 것을 차단하고 클라이언트에 일관된 `400 Bad Request` 응답을 제공할 수 있다.

따라서 현재 규모에서 별도의 전역 API 오류 응답 구조를 먼저 도입하기보다, 실제 API가 확장되어 공통화의 필요성이 커지는 시점에 전역 예외 처리로 전환하는 것이 적절하다고 판단했다.

이와 별도로, 클라이언트에서도 빈 내용 입력을 먼저 확인하여 불필요한 요청을 줄이고, 빠르게 사용자에게 안내하는 방식을 사용한다.

다만 클라이언트 검증은 우회될 수 있으므로, 요청 데이터의 유효성을 최종적으로 보장하는 책임은 서버에 둔다.

### 결과

- 댓글 작성·수정 validation 실패 시 `400 Bad Request` 반환
- validation 실패 응답을 `message` 필드를 가진 JSON 형식으로 통일
- DTO에 정의한 필드별 validation 메시지 활용
- 서버 validation 실패 시 서비스 계층 호출 차단
- 클라이언트 사전 검증을 통한 불필요한 요청 감소
- 클라이언트 사전 검증과 서버 최종 검증의 책임 구분
- Controller 내부 공통 메서드를 통한 오류 처리 중복 감소
- validation 대상 API 확장 시 전역 API 예외 처리로 전환 필요

# 8. 구현 전략 및 리팩토링 계획

## AD-017. Spring Data JPA Page/Pageable 미사용

### 배경

Spring Data JPA는 `Page`와 `Pageable`을 통해 페이징 처리를 추상화하여 제공한다.  
하지만 초기 구현 단계에서는 해당 추상화를 바로 적용하기보다, offset/limit 기반 조회와 페이지 계산 로직을 직접 구현하여 게시판 페이징 요구사항을 명확히 검증하고자 했다.  
이는 `Page`와 `Pageable`을 사용하지 않기 위한 결정이 아니라, 직접 구현한 페이징 정책과 프레임워크가 제공하는 페이징 추상화를 비교하기 위한 단계적 구현 전략이다.

### 결정

초기 구현에서는 Spring Data JPA의 `Page`, `Pageable`을 사용하지 않고, 게시판 페이징을 직접 구현한다.

### 이유

직접 구현을 통해 다음 요소를 명시적으로 설계하고 검증하기 위함이다.

- offset/limit 기반 목록 조회
- 전체 게시글 수 계산
- 전체 페이지 수 계산
- 페이지 블록 계산
- 이전/다음 페이지 이동 기준
- 잘못된 페이지 요청에 대한 clamp 보정

이후 `Page`와 `Pageable` 기반으로 리팩토링하면서, 직접 구현 방식과 프레임워크 제공 방식의 차이점 및 장단점을 비교한다.

### 결과

- 게시판 페이징 요구사항 직접 제어
- 페이징 계산 기준과 보정 정책을 명확히 문서화
- 직접 구현 방식과 `Page`/`Pageable` 방식의 비교 기준 확보
- 향후 Spring Data JPA 페이징 추상화로 리팩토링 가능

### 향후 계획

직접 구현한 방식과 Spring Data JPA의 `Page`/`Pageable`을 비교 분석한 뒤 프레임워크 추상화를 활용하는 방식으로 리팩토링을 검토한다.
